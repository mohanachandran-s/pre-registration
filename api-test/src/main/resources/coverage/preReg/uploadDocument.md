**About this endpoint**

<!-- ENDPOINT:details -->
**What this endpoint does**

Uploads one document (a scanned ID, proof of address, etc.) for a pre-registration application, tagged with a category (`docCatCode` — e.g. `POA` Proof of Address, `POI` Proof of Identity) and a specific document type within that category (`docTypCode`). An application typically needs several of these uploaded before it can proceed to appointment booking. This subject's YAML is the largest in the module by far — most of its 47 cases are the same positive upload repeated against many different upstream application states (freshly created, rebooked, fully-deleted-then-reused, appointment-canceled, etc.) to prove the upload path tolerates all of them, not because the upload logic itself differs.

**Request & response**

Multipart form data — a JSON part (`Document request`) plus the file part:
```
POST /preregistration/v1/documents/{preRegistrationId}
Content-Type: multipart/form-data

Document request: {
  "id": "mosip.pre-registration.document.upload",
  "version": "1.0",
  "requesttime": "2026-08-10T10:00:00.000Z",
  "request": { "docCatCode": "POA", "docTypCode": "RNC", "langCode": "eng" }
}
file: <binary PDF>
```
On success:
```json
{
  "response": {
    "docId": "98745627893456",
    "docName": "doc_POA.pdf",
    "docCatCode": "POA",
    "docTypCode": "RNC",
    "docFileFormat": "pdf"
  },
  "errors": null
}
```
On a validation failure (bad/missing `docCatCode`, `docTypCode`, or `langCode`), `errors[0].errorCode` identifies the field.

**Who can call it**

Only the applicant themselves (`INDIVIDUAL`) may upload a document — unlike most read endpoints in this module, registration-centre staff are **not** on this endpoint's role list at all. Anyone else is rejected with HTTP 403. _(How the login credential itself is transported is the same for every endpoint in this module — see `README.md`'s "How authentication works in this module".)_

<details>
<summary>Technical details (automation + verification notes)</summary>

**Where the role rule lives:** `@PreAuthorize("hasAnyRole(@authorizedRoles.getPostdocumentspreregistrationid())")` on `DocumentController.fileUpload`; roles configured via `mosip.role.prereg.postdocumentspreregistrationid` = `INDIVIDUAL` only. Verified against the live controller source — every document-mutation endpoint in this module (`upload`, `copy`, `updateDocRefId`, both deletes) is similarly restricted to `INDIVIDUAL` alone, in contrast to the broader read/write role lists seen on `DemographicController`/`ApplicationController` endpoints elsewhere in this module.

**Automation mechanic:** the wired script class (`PostWithFormPathParamAndFile`) sends a real `multipart/form-data` POST built from the YAML's `filePath`/`fileKeyName` fields plus the fixture PDFs checked into this subject's folder (`doc_POA.pdf`, `doc_POI.pdf`, `doc_POB.pdf`, `doc_POR.pdf`). A fifth fixture, `morethan1mbsmoke.pdf`, is present on disk but not referenced by any current YAML case — likely intended for a file-size-boundary test that was never wired up (see the `boundary` placeholder row above).

**Error codes are stable, unlike the `PRG_PAM_CORE_*` family:** `DocumentErrorCodes` (the enum backing `PRG_PAM_DOC_*`) is a plain enum with no `.getCode()` override, so `.toString()` always equals the constant's own name — no divergence risk. The `PRG_CORE_REQ_014`/`_017`/`_018` codes used for `langCode`/`docTypCode`/`docCatCode` validation come from the shared `pre-registration-core` `ErrorCodes` enum, but unlike the `PRG_CORE_REQ_001`-`_012` range (which diverges from its own `.getCode()` value — see `createPrereg.md` row `TC_Prereg_CreatePrereg_17`), `_013` upward all have `.getCode()` equal to their own name. Verified against `ErrorCodes.java` directly — no fragility to flag for any row in this subject.
