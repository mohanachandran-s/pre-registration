**About this endpoint**

<!-- ENDPOINT:details -->
**What this endpoint does**

Fetches just the application-tracking status (e.g. `Application_Incomplete`, `Booked`, `Cancelled`) for a single application by its `applicationId` — the tracking-table counterpart to `GetApplicationStatusWithPrId.md`'s demographic-side status read. This one comes from `ApplicationController`, not `DemographicController`.

**Request & response**

No request body — `applicationId` is a path parameter:
```
GET /preregistration/v1/applications/status/{applicationId}
```
On success, the response is a plain string, not a nested object:
```json
{
  "response": "Cancelled",
  "errors": null
}
```
On failure (ID not found), `errors[0].errorCode` = `PRG_APP_013`.

**Who can call it**

Only a registration-centre officer, supervisor, or admin, or the applicant themselves, may check an application's status this way. Anyone else is rejected with HTTP 403. _(How the login credential itself is transported is the same for every endpoint in this module — see `README.md`'s "How authentication works in this module".)_

**Where the role rule lives:** `@PreAuthorize("hasAnyRole(@authorizedRoles.getGetapplicationsstatus())")` on `ApplicationController.getApplicationStatus`; roles configured via `mosip.role.prereg.getapplicationsstatus` = `REGISTRATION_OFFICER, INDIVIDUAL, REGISTRATION_SUPERVISOR, REGISTRATION_ADMIN`. Verified against the live controller source. (Note this is the same role-property *name* `GetApplicationStatusWithPrId.md`'s endpoint uses, but that one also allows `PRE_REGISTRATION_ADMIN` — the two endpoints happen to be configured with different values under a similarly-named property, not the same shared list.)

**Not the same endpoint as `GetApplicationStatusWithPrId.md`:** despite the similar name and purpose, this one is `ApplicationController.getApplicationStatus` (tracking-table status, keyed by `applicationId`, plain-string response), while that one is `DemographicController.getPreRegApplicationStatus` (demographic-record status, keyed by `preRegistrationId`, `PreRegistartionStatusDTO` response). Confirmed by reading both controllers directly — worth calling out since the naming makes them easy to conflate.

**The positive case's asserted value is never actually checked** — see the Notes on row `TC_prereg_GetApplicationStatusByApplicationID_01` above; `checkErrorsOnlyInResponse: true` means the YAML's `"response": "Cancelled"` is decorative.
