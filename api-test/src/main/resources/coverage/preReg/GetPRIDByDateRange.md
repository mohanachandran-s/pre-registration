**About this endpoint**

<!-- ENDPOINT:details -->
**What this endpoint does**

A batch-sync endpoint used by registration-centre client software (not applicant-facing) to pull the list of pre-registration IDs booked at a given centre within a date range — the mechanism a centre's local system uses to know which applicants to expect. It's the heaviest-validated read endpoint in this module: almost every field on the request has its own dedicated negative case.

**Request & response**

```json
{
  "id": "mosip.pre-registration.datasync.fetch.ids",
  "version": "1.0",
  "requesttime": "2026-08-07T10:00:00.000Z",
  "registrationCenterId": "10003",
  "fromDate": "2020-05-09",
  "toDate": "2030-10-11"
}
```
On success, the response echoes the request `id` alongside the matching pre-registration IDs. On a validation failure, `errors[0].errorCode` identifies which field failed and how (see the grid above for the specific code per field/failure combination).

**Who can call it**

Only registration-centre officers, supervisors, or admins may call this sync endpoint — notably, unlike most other read endpoints in this module, a plain `INDIVIDUAL` applicant is not on the allowed list. Anyone else is rejected with HTTP 403. _(How the login credential itself is transported is the same for every endpoint in this module — see `README.md`'s "How authentication works in this module".)_

<summary>Technical details (automation + verification notes)</summary>

**Where the role rule lives:** `@PreAuthorize("hasAnyRole(@authorizedRoles.getPostpreregsync())")` on `DataSyncController`'s `/sync` mapping; roles configured via `mosip.role.prereg.postpreregsync` = `REGISTRATION_OFFICER, REGISTRATION_SUPERVISOR, REGISTRATION_ADMIN` (in `pre-registration-datasync-service`'s `application.properties` — this endpoint lives in a separate service module from most of this batch's other subjects). Verified against the live controller source.

**This is a different microservice from the rest of this batch:** `DataSyncController` is part of `pre-registration-datasync-service`, not `pre-registration-application-service` — worth knowing since its error codes, validator, and role property file are all in a different module than the `DemographicController`/`ApplicationController` endpoints documented elsewhere in this batch.

**Local validation order, confirmed against `DataSyncServiceUtil.validateDataSyncRequest`:** `registrationCenterId` null-check → `fromDate` null-or-format check → `toDate` format check (only if non-blank) → `fromDate`-after-`toDate` check. This exact order explains why a blank/missing `toDate` produces a different (downstream) error than a malformed-but-present one — see the ⚠️ notes on rows `_11`/`_17`/`_18` above.
