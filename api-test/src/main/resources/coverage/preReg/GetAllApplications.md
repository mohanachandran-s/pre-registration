**About this endpoint**

<!-- ENDPOINT:details -->
**What this endpoint does**

Lists every application the currently logged-in user owns, optionally filtered down to one booking type (`NEW_PREREGISTRATION`, `LOST_FORGOTTEN_UIN`, or `UPDATE_REGISTRATION`). It's the "my applications" list view — the same data a portal dashboard would show an applicant, or a registration-centre operator reviewing a specific applicant's history.

**Request & response**

No request body. Two call shapes exist for the one controller method, driven by whether `type` is supplied:
```
GET /preregistration/v1/applications
GET /preregistration/v1/applications?type=NEW_PREREGISTRATION
```
On success:
```json
{
  "response": {
    "allApplications": [
      {
        "applicationId": "98745627893456",
        "bookingType": "NEW_PREREGISTRATION",
        "applicationStatusCode": "Application_Incomplete",
        "bookingStatusCode": null
      }
    ]
  },
  "errors": null
}
```
On an invalid `type` value, `errors[0].errorCode` = `PRG_APP_016`.

**Who can call it**

Only a registration-centre officer, supervisor, or admin, or the applicant themselves, may list applications this way. Anyone else is rejected with HTTP 403. _(How the login credential itself is transported is the same for every endpoint in this module — see `README.md`'s "How authentication works in this module".)_

<summary>Technical details (automation + verification notes)</summary>

**Where the role rule lives:** `@PreAuthorize("hasAnyRole(@authorizedRoles.getGetapplicationsall())")` on `ApplicationController.getAllApplications`; roles configured via `mosip.role.prereg.getapplicationsall` = `REGISTRATION_OFFICER, INDIVIDUAL, REGISTRATION_SUPERVISOR, REGISTRATION_ADMIN`. Verified against the live controller source.

**One controller method, one query parameter, two YAML "units":** `ApplicationController.getAllApplications(@RequestParam(required = false) String type)` branches internally — `type == null` calls `getAllApplicationsForUser()`, a non-null `type` calls `getAllApplicationsForUserForBookingType(type)`. The suite models this as two separate units (based on whether the YAML's `endPoint:` string includes the `?type={type}` query template), which is a reasonable split since the two branches have genuinely different validation (the `type` branch checks the value against the three known booking types; the no-`type` branch has no equivalent check).

**Same underlying data, different subject:** `GetAllPreRegApplications.md` documents the exact same no-`type` call (`GET /applications`, same controller method, same `getAllApplicationsForUser()` branch) under a different subject name — not a bug, just how the suite organizes scenarios for this endpoint.
