**About this endpoint**

**What this endpoint does**

Same purpose as `FetchApplicationByPrid.md` — fetches the full demographic identity record for a pre-registration application. This subject's YAML happens to test that endpoint for the positive case, but (per the 🛑 finding below) its negative case actually lands on the different `/applications/prereg/info/{id}` endpoint that `GetPreRegInfoByPrid.md` documents.

**Request & response**

For the intended `/applications/prereg/{preRegistrationId}` unit, see `FetchApplicationByPrid.md`'s Request & response — identical endpoint, identical flat `DemographicResponseDTO` response shape. For the `/applications/prereg/info/{preRegistrationId}` unit this subject's negative case actually hits, see `GetPreRegInfoByPrid.md`.

**Who can call it**

Same role list as `FetchApplicationByPrid.md` for the intended unit (`getapplications` = `REGISTRATION_OFFICER, INDIVIDUAL, REGISTRATION_SUPERVISOR, REGISTRATION_ADMIN, PRE_REGISTRATION_ADMIN`); see `GetPreRegInfoByPrid.md`'s role list (`getapplicationsinfo`, same role values) for the `info` unit. _(How the login credential itself is transported is the same for every endpoint in this module — see `README.md`'s "How authentication works in this module".)_

<details>
<summary>Technical details (automation + verification notes)</summary>

**The `endPoint:` mismatch is a real YAML authoring bug, not a framework limitation** — `GetWithParam` (the wired test-script class) sends whatever `endPoint:` the YAML declares for each case, so nothing here is a tooling constraint; the negative case's `endPoint:` simply doesn't match its own subject's positive case. Kept documented rather than fixed, per this pass's scope (matching how `DeleteLostUinApplication.md` handles its own endpoint-mismatch finding).

**Why the asserted error code still happens to be correct:** `DemographicService.getPregistrationInfo` (the `info` endpoint's handler) calls `getDemographicData(prid)` internally and lets its exceptions propagate — the same method `getPreRegDemographicData` (this subject's intended endpoint) calls directly. So a not-found `preRegistrationId` produces `PRG_PAM_APP_005` from either endpoint, which is why this test still "passes" despite hitting the wrong one. Verified against both controller methods' source.

**Two subjects, one real endpoint, split unevenly:** `FetchApplicationByPrid.md` carries this endpoint's only genuinely-attributed positive and not-found coverage. This subject's only unique contribution is the dependency-chain positive case (`dateOfBirth` sourced from a distinct `createPrereg` smoke case) — everything else here is either duplicate-endpoint coverage or, for the `info` unit, currently unautomated.
