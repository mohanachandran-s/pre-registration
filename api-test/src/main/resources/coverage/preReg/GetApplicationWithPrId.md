**About this endpoint**

<!-- ENDPOINT:details -->
**What this endpoint does**

Fetches the stored application-tracking record for a single application by its ID — booking type, current application/booking status, appointment slot, and registration-centre assignment. It reads from the lightweight `applications` tracking table, not the full demographic identity record (that's a separate endpoint — see `FetchApplicationByPrid.md`).

**Request & response**

No request body — `preRegistrationId` is a path parameter:
```
GET /preregistration/v1/applications/{preRegistrationId}
```
On success, the response echoes the tracking record:
```json
{
  "response": {
    "applicationId": "98745627893456",
    "bookingType": "NEW_PREREGISTRATION",
    "applicationStatusCode": "Application_Incomplete",
    "bookingStatusCode": null,
    "registrationCenterId": "10003",
    "appointmentDate": null,
    "bookingDate": null,
    "crBy": "the caller's user ID",
    "crDtime": "2026-08-07T10:00:00.000Z"
  },
  "errors": null
}
```
On failure (ID not found), `errors[0].errorCode` = `PRG_APP_013`.

**Who can call it**

Only a registration-centre officer or the applicant themselves may fetch an application by ID — this endpoint's role list is narrower than most others in this module (no supervisor/admin/pre-registration-admin). Anyone else is rejected with HTTP 403. _(How the login credential itself is transported is the same for every endpoint in this module — see `README.md`'s "How authentication works in this module".)_

<summary>Technical details (automation + verification notes)</summary>

**Where the role rule lives:** `@PreAuthorize("hasAnyRole(@authorizedRoles.getGetapplicationdetailsappid())")` on `ApplicationController.getApplication`; roles configured via `mosip.role.prereg.getapplicationdetailsappid` = `REGISTRATION_OFFICER, INDIVIDUAL` — notably narrower than the `getapplications`/`getapplicationsall` role lists most other read endpoints in this module use (those also allow `REGISTRATION_SUPERVISOR`, `REGISTRATION_ADMIN`, and sometimes `PRE_REGISTRATION_ADMIN`). Verified against the live controller source.

**Same endpoint, two subjects:** `GET /applications/{applicationId}` is also the exact endpoint `GetAllApplicationsWithapplicationId.md` documents — same controller method (`ApplicationController.getApplication`), same path shape, just a different `{id}` variable name in each subject's YAML. Not a bug; the suite simply organizes scenarios for this one endpoint under two subject names. Treat the two files as covering one real endpoint jointly rather than expecting either alone to be complete.

**Unused/inaccurate leftover template:** `getApplicationWithPrIdResult.hbs` on disk defines an elaborate `demographicDetails.identity.*` response shape (gender, city, fullName, etc.) — but the subject's one test case uses `preReg/error` as its `outputTemplate`, so this file is never actually exercised. It also wouldn't match reality if it were: the real response is `ApplicationEntity` (`applicationId`, `bookingType`, `applicationStatusCode`, ...), which has no `demographicDetails` field at all — that shape belongs to the different `DemographicResponseDTO` returned by `FetchApplicationByPrid`'s endpoint. Left as-is since nothing references it, but worth knowing if this subject ever gets a positive case authored.
