**About this endpoint**

<!-- ENDPOINT:details -->
**What this endpoint does**

Creates a new application record for someone who already has a UIN and wants to update/correct their registration data at a registration centre — a different flow from `createPrereg`, which is for a brand-new identity. Functionally it's the sibling of `AddLostUinApplication`: both endpoints delegate to the same underlying "add application" service method, just tagged with a different booking type (`UPDATE_REGISTRATION` here, `LOST_FORGOTTEN_UIN` there) so downstream steps (appointment booking, registration-centre processing) know which workflow they're handling.

**Request & response**

The request body is deliberately minimal — just a language code, wrapped in the standard envelope:
```json
{
  "id": "mosip.pre-registration.updateregistration.create",
  "version": "1.0",
  "requesttime": "2026-08-07T10:00:00.000Z",
  "langCode": "eng"
}
```
On success, the response confirms the new application and its initial state:
```json
{
  "id": "mosip.pre-registration.updateregistration.create",
  "version": "1.0",
  "responsetime": "2026-08-07T10:00:01.000Z",
  "response": {
    "applicationId": "98745627893456",
    "createdBy": "the caller's user ID",
    "createdDateTime": "2026-08-07T10:00:01.000Z",
    "applicationStatusCode": "SUBMITTED",
    "bookingStatusCode": null,
    "langCode": "eng",
    "bookingType": "UPDATE_REGISTRATION"
  },
  "errors": null
}
```

**Who can call it**

Only the applicant themselves, or registration-centre staff (an officer, supervisor, or admin) acting on the applicant's behalf, may submit an update-registration application. Anyone else is rejected with HTTP 403. _(How the login credential itself is transported is the same for every endpoint in this module — see `README.md`'s "How authentication works in this module".)_

Verified against the live controller source.

**Building the request body:** unlike `createPrereg`/`UpdatePreregistration`, this request template is a plain static `.hbs` file (`addUpdateRegistration.hbs`), not dynamically generated from the live ID Schema — the request body genuinely is just `langCode`, so there's no per-field schema derivation needed here.
