**About this endpoint**

<!-- ENDPOINT:details -->
**What this endpoint does**

A combined "everything about this application" read: fetches the demographic identity data (the same data `FetchApplicationByPrid` returns) and, if any exist, the applicant's uploaded document metadata, in one call. It exists so a caller who needs both doesn't have to make two separate requests.

**Request & response**

No request body — `preRegistrationId` is a path parameter:
```
GET /preregistration/v1/applications/prereg/info/{preRegistrationId}
```
On success:
```json
{
  "response": {
    "demographicResponse": {
      "preRegistrationId": "98745627893456",
      "statusCode": "Pending_Appointment",
      "demographicDetails": {
        "identity": {
          "postalCode": "14022",
          "dateOfBirth": "1996/01/01",
          "phone": "8249742850",
          "email": "goku@hogwarts.co.in"
        }
      }
    },
    "documentsMetaData": null
  },
  "errors": null
}
```
On failure (ID not found), `errors[0].errorCode` = `PRG_PAM_APP_005`. If the demographic lookup succeeds but no documents are on file, `documentsMetaData` is simply absent/null rather than an error — the document lookup failure is swallowed internally (see Technical details).

**Who can call it**

Only the applicant themselves, or registration-centre staff (an officer, supervisor, admin, or pre-registration admin) acting on the applicant's behalf, may fetch this combined view. Anyone else is rejected with HTTP 403. _(How the login credential itself is transported is the same for every endpoint in this module — see `README.md`'s "How authentication works in this module".)_

<details>
<summary>Technical details (automation + verification notes)</summary>

**Where the role rule lives:** `@PreAuthorize("hasAnyRole(@authorizedRoles.getGetapplicationsinfo())")` on `DemographicController.getPreRegDemographicAndDocumentData`; roles configured via `mosip.role.prereg.getapplicationsinfo` = `REGISTRATION_OFFICER, INDIVIDUAL, REGISTRATION_SUPERVISOR, REGISTRATION_ADMIN, PRE_REGISTRATION_ADMIN`. Verified against the live controller source.

**Genuinely nested response, unlike `FetchApplicationByPrid`:** `DemographicService.getPregistrationInfo` returns `ApplicationInfoMetadataDTO { demographicResponse: DemographicResponseDTO, documentsMetaData }` — the extra `demographicResponse` wrapper key is real here (confirmed against `ApplicationInfoMetadataDTO`'s field list and `getPreRegInfoByPridResult.hbs`'s matching nesting), in contrast to `FetchApplicationByPrid`/`GetPreRegDemographicDataByPrid`, whose endpoint returns `DemographicResponseDTO` flat with no such wrapper. Worth knowing before assuming the two response shapes are interchangeable.

**Document lookup failure is caught internally:** `getPregistrationInfo` wraps its call to fetch document metadata in its own try/catch for `PreRegistrationException`/`DocumentNotFoundException`, logging and continuing rather than failing the whole request — so an application with no documents yet still returns a normal 200 with `documentsMetaData` unset, not an error.
