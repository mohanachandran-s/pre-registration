**About this endpoint**

<!-- ENDPOINT:details -->
**What this endpoint does**

Discards a booked appointment and, unlike `CancelApplicationsAppointment.md`'s cancel operation, also updates the application's status as part of removing the booking record entirely — a heavier operation than a plain cancel (see Technical details).

**Request & response**

No request body — `preRegistrationId` is a required query parameter:
```
DELETE /preregistration/v1/applications/appointment?preRegistrationId={preRegistrationId}
```
On success:
```json
{
  "response": { "deletedBy": "the caller's user ID" },
  "errors": null
}
```

**Who can call it**

The applicant themselves, a registration-centre officer, or a pre-registration admin may discard a booking. Anyone else is rejected with HTTP 403. _(How the login credential itself is transported is the same for every endpoint in this module — see `README.md`'s "How authentication works in this module".)_

**Where the role rule lives:** `@PreAuthorize("hasAnyRole(@authorizedRoles.getDeleteappointmentpreregid())")` on `AppointmentController.discardIndividual`; roles configured via `mosip.role.prereg.deleteappointmentpreregid` = `REGISTRATION_OFFICER, INDIVIDUAL, PRE_REGISTRATION_ADMIN`. Verified against the live controller source.

**Distinct from cancel:** the controller delegates to `appointmentService.deleteBookingAndUpdateApplicationStatus(preId)` — a different service method from `cancelAppointment(preId)` (which backs `CancelApplicationsAppointment.md`). The method name implies this operation additionally rolls the application's status back, not just removes the booking row; not independently traced to the exact status transition in this pass.
