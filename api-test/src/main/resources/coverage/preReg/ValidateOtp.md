**About this endpoint**

<!-- ENDPOINT:details -->
**What this endpoint does**

Redeems the OTP sent by `SendOtp.md`, completing the login flow — on success, the server issues the `Authorization` cookie that every other endpoint in this module reads to authenticate the caller. This is literally where that cookie originates.

**Request & response**

```
POST /preregistration/v1/login/validateOtp
{
  "id": "mosip.pre-registration.login.useridotp",
  "version": "1.0",
  "requesttime": "2026-08-11T10:00:00.000Z",
  "request": { "userId": "user@example.com", "otp": "123456" }
}
```
On success, the response body confirms the login and the `Authorization` cookie is set on the HTTP response (not part of the JSON body). On failure, `errors[0].errorCode` = `KER-OTV-005` (invalid OTP) — a Kernel OTP-validator error code, not one of this module's own `PRG_*` codes, confirming OTP correctness is checked by a shared Kernel service rather than this module's own logic.

**Who can call it**

Unauthenticated — this endpoint is what *produces* the login credential, so (like `SendOtp.md`) it doesn't sit behind the cookie-based authorization every other endpoint in this module requires. _(See `README.md`'s "How authentication works in this module" for how the credential this endpoint issues is used elsewhere.)_

<details>
<summary>Technical details (automation + verification notes)</summary>

**Where the login-cookie issuance lives:** `LoginController.validateWithUserIdOtp` — on a response with no `errors`, it calls `loginService.getLoginToken(userId, requestUri)` and attaches the result as an `HttpOnly`, `Secure` cookie named `Authorization`. This is the definitive source for the cookie-based auth mechanism documented in `README.md`.

**`"DYNAMICOTP"` is not a recognized dynamic-substitution token anywhere in this codebase** — grepped both this module's test-script source and `apitest-commons` for the literal string; zero hits. Every case in this subject sends it as a plain literal value, not a captured/generated real OTP. Row `_01`'s success therefore depends entirely on server-side/environment OTP configuration (e.g. a configured static test-mode OTP accepted in non-production environments) rather than anything this repository's automation does to generate a valid one — worth confirming against the target environment's OTP-manager configuration if this subject is ever re-authored.
</details>
