**About this endpoint**

**What this endpoint does**

🛑 **This section describes what the endpoint is *supposed* to be — every test case in this subject actually calls a different, wrong endpoint. See the Notes on row `TC_prereg_DeleteLostUinApplication_01` above for the full analysis.**

The real Lost-UIN delete endpoint (`DELETE /applications/lostuin/{applicationId}`) should let an applicant, or registration-centre staff on their behalf, withdraw a lost-UIN-recovery application they previously submitted via `AddLostUinApplication`. Instead, every case in this subject calls the generic `DELETE /applications/prereg/{applicationId}` endpoint — the exact same one `DeletePreRegistration.md` documents — against records created through the ordinary `createPrereg` flow, never through `AddLostUinApplication`. As a result, this subject provides real coverage of the generic delete endpoint (already documented once in `DeletePreRegistration.md`) and **zero** real coverage of the Lost-UIN delete endpoint its name and every case description claim to test.

**Request & response**

The real Lost-UIN delete endpoint, if these tests called it, would look like the generic delete endpoint they actually call today — no request body, `applicationId` as a path parameter only:
```
DELETE /preregistration/v1/applications/lostuin/{applicationId}
```
`ApplicationServiceIntf.deleteLostOrUpdateApplication` returns a `MainResponseDTO<DeleteApplicationDTO>` on success — structurally similar to the generic delete's `DeletePreRegistartionDTO` response (`applicationId`, who deleted it, when), though the exact `DeleteApplicationDTO` field names weren't independently verified for this pass.

**Who can call it**

Intended to be: only the applicant themselves, or registration-centre staff (an officer, supervisor, or admin) acting on the applicant's behalf. Anyone else would be rejected with HTTP 403 — the same role set as every other delete/create endpoint in this module. _(How the login credential itself is transported is the same for every endpoint in this module — see `README.md`'s "How authentication works in this module".)_

<summary>Technical details (automation + verification notes)</summary>

**Where the role rule would live:** `@PreAuthorize("hasAnyRole(@authorizedRoles.getDeleteapplications())")` on `LostUINController.deleteLostUinApplication`; roles configured via `mosip.role.prereg.deleteapplications` = `INDIVIDUAL, REGISTRATION_OFFICER, REGISTRATION_SUPERVISOR, REGISTRATION_ADMIN` — the same property `DeletePreRegistration`/`AddUpdateRegistration`'s delete method use. Verified against the live controller source; this is the rule the tests *would* be exercising if they called the right endpoint — since they don't, this subject currently only proves the *generic* delete endpoint's role rule works (already covered by `DeletePreRegistration.md`).

**The wrong-endpoint bug, restated for the automation side:** every case's `endPoint:` in `DeleteLostUinApplication.yml` is `/preregistration/v1/applications/prereg/{applicationId}`, not `/preregistration/v1/applications/lostuin/{applicationId}`. This is a YAML authoring error, not a framework limitation — `DeleteWithParam` (the wired test-script class) sends whatever `endPoint:` the YAML declares, so fixing the YAML would be enough to start exercising the real endpoint. Per this pass's scope, this is documented only, not fixed.
