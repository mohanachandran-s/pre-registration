**About this endpoint**

<!-- ENDPOINT:details -->
**What this endpoint does**

Lists every booking (application) at a given registration centre within a date range — the registration-centre-facing counterpart to an applicant checking their own single appointment; this is what centre staff would use to see their full day's/week's schedule.

**Request & response**

No request body — `regCenterId` is a path parameter, `appointmentDate`/`appointmentToDate` are query parameters:
```
GET /preregistration/v1/applications/bookings/{regCenterId}?appointmentDate=2026-08-20&appointmentToDate=2026-08-27
```
On success, the response lists matching bookings (no specific fields are asserted by any current test — `checkErrorsOnlyInResponse: true`). On failure, `errors[0].errorCode` = `PRG_APP_012` (no bookings found), `PRG_APP_013` (invalid `regCenterId` format or unparseable date).

**Who can call it**

Registration-centre officers, supervisors, admins, or an applicant (`INDIVIDUAL`) may call this. Anyone else is rejected with HTTP 403. _(How the login credential itself is transported is the same for every endpoint in this module — see `README.md`'s "How authentication works in this module".)_

<summary>Technical details (automation + verification notes)</summary>

**Where the role rule lives:** `@PreAuthorize("hasAnyRole(@authorizedRoles.getGetappointmentregistrationcenterid())")` on `ApplicationController.getBookingsForRegCenter`; roles configured via `mosip.role.prereg.getappointmentregistrationcenterid` = `INDIVIDUAL, REGISTRATION_OFFICER, REGISTRATION_SUPERVISOR, REGISTRATION_ADMIN`. Verified against the live controller source (the same `ApplicationController` documented in `GetAllApplications.md`/`GetApplicationWithPrId.md` from batch 3).

**Validation order, confirmed against `ApplicationService.getBookingsForRegCenter`:** `regCenterId` format check (`InvalidIDException` → `PRG_APP_013`) → `appointmentFromDate` parse (`DateTimeParseException` → `PRG_APP_013`) → `appointmentToDate` parse (same) → repository lookup (`null` → `PRG_APP_012`). This exact order is what makes row `_03`'s 🛑 finding provable — `regCenterId` validation always runs first, so a malformed `regCenterId` can never reach whatever branch would produce `PRG_BOOK_RCI_032`, regardless of the date fields.

**Same `PRG_BOOK_RCI_032` code, different endpoint** — `GetPRIDByDateRange.md` (batch 3) and `GetPRIDForRegCent.md` (this batch) both assert this code for their own invalid-registration-centre scenarios, and in both of those cases it's unverifiable (no source in this repo defines it). This file's row `_03` is the one case in the whole codebase where the *same* code is asserted but demonstrably wrong, because this endpoint's validation path is fully traceable and doesn't go near it.
