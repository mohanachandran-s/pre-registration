**About this endpoint**

<!-- ENDPOINT:details -->
**What this endpoint does**

Deletes a single uploaded document from an application. If the deleted document was one of the mandatory documents required for the application's category and the application was already in "Pending Appointment" status, this also demotes the application back to "Application Incomplete" — deleting a required document un-completes the application.

**Request & response**

No request body — `documentId` is a path parameter, `preRegistrationId` is a required query parameter:
```
DELETE /preregistration/v1/documents/{documentId}?preRegistrationId={preRegistrationId}
```
On success, `response.message` confirms the deletion. On failure, `errors[0].errorCode` identifies the problem — `PRG_PAM_APP_005` if the `preRegistrationId` doesn't exist, `PRG_PAM_DOC_022` if the `documentId` exists but belongs to a different application.

**Who can call it**

Only the applicant themselves (`INDIVIDUAL`) may delete a document. Anyone else is rejected with HTTP 403. _(How the login credential itself is transported is the same for every endpoint in this module — see `README.md`'s "How authentication works in this module".)_

**Where the role rule lives:** `@PreAuthorize("hasAnyRole(@authorizedRoles.getDeletedocumentsdocumentid())")` on `DocumentController.deleteDocument`; roles configured via `mosip.role.prereg.deletedocumentsdocumentid` = `INDIVIDUAL` only. Verified against the live controller source.

**`restMethod` in the YAML isn't authoritative for the real HTTP verb** — the same finding as `UpdatePreRegStatus.md`'s gotcha, found again here: `DeleteSpecificDocForaPRID.yml` declares `restMethod: post`, but the suite wires this subject to `DeleteWithParam`, which unconditionally calls `deleteWithPathParamAndCookie(...)` and never reads `testCaseDTO.getRestMethod()` — so the real verb is `DELETE`, matching the actual `@DeleteMapping` on `DocumentController.deleteDocument`. Confirmed via the wired script class's source.

**Deleting a mandatory document can silently change the application's status** — `deleteDocument` checks `serviceUtil.validMandatoryDocuments(...)` and, if the deleted document was mandatory and the application was `Pending_Appointment`, calls `serviceUtil.updateApplicationStatusToIncomplete(...)`. None of this subject's current cases assert on the resulting `applicationStatusCode` afterward — a case that deletes a mandatory document and then checks `GetApplicationStatusWithPrId` would give this real side effect actual coverage.
