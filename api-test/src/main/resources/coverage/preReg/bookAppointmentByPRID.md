**What this endpoint does**

Books an appointment the same way `bookAppointment.md` does, but with `preRegistrationId` supplied in the request body instead of the URL path. Despite the "by PRID" name suggesting a single-application booking, this subject actually exercises `AppointmentController.bookMultiAppoinment` — the endpoint designed for booking *multiple* applications' appointments in one call (`MultiBookingRequest`) — just with a request that happens to contain one entry. Confirmed by matching the YAML's path-variable-free `POST /applications/appointment` against the controller source; `bookAppointment.md`'s endpoint (`POST /applications/appointment/{preRegistrationId}`) is the genuinely single-application version.

**Request & response**

```
POST /preregistration/v1/applications/appointment
{
  "id": "mosip.pre-registration.booking.book",
  "version": "1.0",
  "requesttime": "2026-08-11T10:00:00.000Z",
  "preRegistrationId": "98745627893456",
  "registration_center_id": "10003",
  "appointment_date": "2026-08-20",
  "time_slot_from": "09:00:00",
  "time_slot_to": "09:15:00"
}
```
On success, no distinct fields are asserted by any current test (`checkErrorsOnlyInResponse: true`). On failure, `errors[0].errorCode` identifies the problem — see the grid above.

**Who can call it**

The applicant themselves, or a registration-centre officer acting on their behalf, may book an appointment this way. Anyone else is rejected with HTTP 403. _(How the login credential itself is transported is the same for every endpoint in this module — see `README.md`'s "How authentication works in this module".)_
