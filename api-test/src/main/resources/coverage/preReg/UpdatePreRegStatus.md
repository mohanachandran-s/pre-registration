**About this endpoint**

**What this endpoint does**

Updates a pre-registration application's lifecycle status (e.g. into `Pending_Appointment`). Status gates what an applicant/operator can do next — book a slot, get flagged expired, and so on — so this is a key transition threaded through nearly every downstream prereg flow. That's why most rows below exist purely to put a pre-registration into the right status for some other subject's test.

⚠️ **The `Units` line above says `GET ...` — that's mechanically pulled from this YAML's `restMethod: get` field, and it's inaccurate.** Verified directly against the wired test-script class, `PutWithPathParam.java`: it calls `putWithPathParamAndCookie(...)` unconditionally and never reads `testCaseDTO.getRestMethod()` anywhere in the class — every case in `updatePreRegStatus.yml` actually sends a real `PUT` request no matter what `restMethod:` says. The endpoint every row below genuinely exercises is `PUT /preregistration/v1/applications/prereg/status/{preRegistrationId}?statusCode={statusCode}`. This is a YAML-metadata inaccuracy, not a functional bug — the tests do hit the intended endpoint — but it means `restMethod` can't be trusted as ground truth for the HTTP verb in this module (the wired `<class>` in `preregSuite.xml` is what actually decides it), and this coverage-matrix estate's own `Inventory` tool inherited that inaccuracy into the "Units" line above. Recommend correcting `restMethod: get` → `restMethod: put` in the YAML for documentation accuracy (done 2026-09-25 — `check`'s `verb-mismatch` gap now enforces it).

**Request & response**

No JSON body — this is a path + query parameter call:
```
PUT /preregistration/v1/applications/prereg/status/{preRegistrationId}?statusCode=Pending_Appointment
```
On success:
```json
{
  "id": "mosip.pre-registration.status.update",
  "version": "1.0",
  "responsetime": "2026-08-07T10:00:01.000Z",
  "response": "STATUS_UPDATED_SUCESSFULLY",
  "errors": null
}
```

**Who can call it**

Only the applicant themselves, registration-centre staff (an officer, supervisor, or admin), or a pre-registration admin may update a pre-registration's status. Anyone else is rejected with HTTP 403. _(How the login credential itself is transported is the same for every endpoint in this module — see `README.md`'s "How authentication works in this module".)_
