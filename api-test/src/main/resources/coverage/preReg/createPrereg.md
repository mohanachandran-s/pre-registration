**About this endpoint**

**What this endpoint does**

Creates a new pre-registration application. This is the very first step in the pre-registration journey: an applicant (or the staff registering them) submits their basic contact and demographic details before ever visiting a registration centre. The unique ID this call hands back is what ties everything afterward together — uploading documents, booking an appointment slot, checking status, and so on all refer back to it. That's also why so many rows in the table below exist purely to "seed" a fixture for some other test — almost nothing else in this module can be tested without a pre-registration application to work against first.

**Request & response**

The caller sends their preferred language plus a handful of demographic details — postal code, phone, email, date of birth — wrapped in MOSIP's standard envelope (an `id`, a `version`, a `requesttime`, and the actual `request` payload):
```json
{
  "id": "mosip.pre-registration.demographic.create",
  "version": "1.0",
  "requesttime": "2026-08-07T10:00:00.000Z",
  "request": {
    "langCode": "eng",
    "demographicDetails": {
      "postalCode": "14022",
      "phone": "8249742850",
      "email": "goku@technoforte.co.in",
      "dateOfBirth": "1996/01/01"
    }
  }
}
```
On success, the response echoes back a new `preRegistrationId` — the ID every later step (documents, appointment booking, status checks) refers back to — along with the application's initial status and when it was created:
```json
{
  "id": "mosip.pre-registration.demographic.create",
  "version": "1.0",
  "responsetime": "2026-08-07T10:00:01.000Z",
  "response": {
    "preRegistrationId": "98745627893456",
    "createdDateTime": "2026-08-07T10:00:01.000Z",
    "statusCode": "Pending_Appointment",
    "langCode": "eng"
  },
  "errors": null
}
```

**Who can call it**

Only the applicant themselves, or registration-centre staff (an officer, supervisor, or admin) acting on the applicant's behalf, are allowed to create a pre-registration. Anyone else — an unauthenticated caller, or someone logged in with an unrelated role — is rejected outright with a "Forbidden" (HTTP 403) error, before any application gets created. _(How the login credential itself is transported — cookie vs. header, how our tests acquire it — is the same for every endpoint in this module; see `README.md`'s "How authentication works in this module" instead of restating it here.)_

<summary>Technical details (automation + verification notes)</summary>

**Where the role rule lives:** enforced via `@PreAuthorize("hasAnyRole(@authorizedRoles.getPostapplications())")` on `DemographicController.addPreRegDemographicData`; the role list — `INDIVIDUAL`, `REGISTRATION_OFFICER`, `REGISTRATION_SUPERVISOR`, `REGISTRATION_ADMIN` — is configured via `mosip.role.prereg.postapplications` in `application.properties`, not hardcoded. Verified directly against the live controller source.

**Building the request body:** unusually for this module, the request template is generated **dynamically at runtime**, not from a static `.hbs` file: `CreatePreReg.test()` calls `AdminTestUtil.generateHbsForPrereg(false)`, which fetches the live ID Schema from the identity-schema service and derives the field list from the schema's `required` array. That's why `createPrereg/` has no `createPrereg.hbs` file on disk — only the YAML and a result template (confirmed by directory listing, not assumed). The YAML `input` values (`postalCode`, `phone`, `email`, `IDSchemaVersion`, `dateOfBirth`, `version`, `langCode`, `requesttime`, `id`) get merged into that generated template at test time.
