**About this endpoint**

<!-- ENDPOINT:details -->
**What this endpoint does**

Fetches one specific document's actual content (decrypted, ready to display/download) by its document ID — the "open this one file" counterpart to `GetAllDocForPrId.md`'s "list everything" view.

**Request & response**

No request body — `documentId` is a path parameter, `preRegistrationId` is a required query parameter:
```
GET /preregistration/v1/documents/{documentId}?preRegistrationId={preRegistrationId}
```
On success:
```json
{
  "response": { "document": "<base64-encoded decrypted file content>" },
  "errors": null
}
```
On failure, `errors[0].errorCode` identifies the problem — `PRG_PAM_APP_005` if the `preRegistrationId` doesn't exist, `PRG_PAM_DOC_022` if the `documentId` exists but belongs to a *different* application than the one named in `preRegistrationId`.

**Who can call it**

The applicant themselves, or registration-centre staff (an officer, supervisor, or admin), may fetch a specific document's content. Anyone else is rejected with HTTP 403. _(How the login credential itself is transported is the same for every endpoint in this module — see `README.md`'s "How authentication works in this module".)_

<summary>Technical details (automation + verification notes)</summary>

**Where the role rule lives:** `@PreAuthorize("hasAnyRole(@authorizedRoles.getGetdocumentsdocumentid())")` on `DocumentController.getDocumentforDocId`; roles configured via `mosip.role.prereg.getdocumentsdocumentid` = `REGISTRATION_OFFICER, REGISTRATION_SUPERVISOR, REGISTRATION_ADMIN, INDIVIDUAL`. Verified against the live controller source.

**🛑 A nonexistent `documentId` likely NPEs rather than producing `PRG_PAM_DOC_005`.** Traced `DocumentService.getDocumentForDocId`: it calls `documnetDAO.findBydocumentId(docId)` and immediately calls `.getDemographicEntity()` on the result with **no null check** — if `docId` doesn't resolve to a row, `findBydocumentId` returns `null` (standard Spring Data behavior for a single-result `findBy` query with no match) and the very next line throws a `NullPointerException`. `PRG_PAM_DOC_005` is only reachable *after* that point, guarded behind a *different* null check (`sourcefile == null`, for a missing object-store file on an otherwise-valid document). Checked `DocumentExceptionCatcher.handle()` directly: its `instanceof` chain covers the module's own checked/unchecked exception hierarchy but has no branch for a plain `NullPointerException`, so it would fall through silently, most likely surfacing as an unhandled 500 (or a response with neither `errors` nor `response` populated) rather than the clean `PRG_PAM_DOC_005` this row asserts. This is a static-code finding — recommend confirming against a live run before treating it as certain, the same caveat as the analogous finding on `UpdateDocRefID.md`.
