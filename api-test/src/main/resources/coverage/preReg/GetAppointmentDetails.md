**About this endpoint**

<!-- ENDPOINT:details -->
**What this endpoint does**

*Intended* to fetch the appointment details (registration centre, date, time slot) booked for a pre-registration application — the read counterpart to `bookAppointment.md`. See the ⚠️ Technical details below for a real concern about whether this subject reaches that endpoint at all.

**Request & response**

No request body — `preRegistrationId` is a path parameter. This subject's YAML uses:
```
GET /preregistration/v1/appointment/{preRegistrationId}
```
On success, the response includes `registration_center_id` among other booking fields (see `FetchAppointmentDetailsByPrid.md` for a fuller documented response shape, since that subject's endpoint is the one confirmed to exist).

**Who can call it**

Intended to be the applicant themselves, or a registration-centre officer, based on the equivalent `getAppointmentdetailspreregid` role rule documented on `FetchAppointmentDetailsByPrid.md`. _(How the login credential itself is transported is the same for every endpoint in this module — see `README.md`'s "How authentication works in this module".)_

**⚠️ This subject's `endPoint:` may not match any real controller mapping.** Every case in `GetAppointmentDetails.yml` uses `/preregistration/v1/appointment/{preRegistrationId}` — missing the `applications/` path segment that `AppointmentController.getAppointments`'s real `@GetMapping` requires (`/applications/appointment/{preRegistrationId}`). `FetchAppointmentDetailsByPrid.yml` is very likely this endpoint's intended, correctly-pathed sibling — its `endPoint:` is exactly `/preregistration/v1/applications/appointment/{preRegistrationId}`, matching the real mapping, and its purpose/description are nearly identical to this subject's. Grepped this repository's controllers for any mapping matching the shorter path (`/appointment/{preRegistrationId}` with no `applications/` prefix) — found none. This is a static-code finding, not a confirmed live-run 404 — worth confirming against a real environment before treating it as certain, but the pattern (a `Get*`-named subject using a shortened path, paired with a `Fetch*`-named sibling using the correct one) repeats identically for `GetAvailableSlotForRegCentreId.md`/`FetchAvailabilityData.md` in this same batch, which strengthens the case that this is a systemic YAML-authoring habit rather than one-off noise.
